# Veredicto de release — CU-1 v0.101.20 (2026-10-17)

> Registro de la promoción de `v0.101.20`, el corte de CU-1 (reliable
> consumption SDK) que desbloquea `v0.101.19`. Este fichero es evidencia
> post-release: se añade después de publicar y no repite la ceremonia del
> JOURNAL; donde dijo una cosa el JOURNAL, manda este documento para la
> release y al revés para el roadmap.

## Por qué v0.101.20 y no v0.101.19

`v0.101.19` pasó 25 stages de RC y falló en `payloads`: `TIER1_PLATFORMS`
declaraba `[LinuxX86_64, LinuxAarch64]` y ninguna lane construye aarch64. La
corrección (#361) cambia código Rust (`TIER1_PLATFORMS: [Platform; 1] =
[Platform::LinuxX86_64]`), así que no podía entrar en un tag ya publicado. El
corte recursivo (opción B) fue `v0.101.20` desde `main@2764a2ab`.

## Defectos latentes encontrados durante el corte

Ninguno bloquea la release publicada. Se listan para que el próximo corte no
los pague otra vez:

1. **RC y release no comparten layout**. Desde E1 (#339) el RC escribe
   `staging/payloads-<plataforma>/dist/`, pero `release.pipeline.kts` exige un
   `dist/` en la raíz. En este corte el `dist/` se materializó desde
   `staging/payloads-linux-x86-64/dist/` (los mismos tres tarballs).
2. **`verify-as-consumer` no resuelve el repo**. Hace `gh release download`
   dentro de `mktemp -d`, fuera de un repo git, sin `-R`/`GH_REPO`; falla con
   `fatal: no es un repositorio git`. Añadir `-R "$GITHUB_REPOSITORY"` (o
   exportar `GH_REPO`) lo arregla.
3. **El contrato golden lee un binario global mutable**. Prefiere
   `/var/home/rubentxu/cargo-targets/release/cognicode`; otro checkout lo
   recompiló a `0.101.19` entre el build y el stage `contracts` y el gate
   falló dos veces por eso. Debería preferir el `CARGO_TARGET_DIR` del run o
   construir el binario desde el árbol.
4. **`build-isolation` cuenta huérfanos propios como ajenos**. Al matar un run
   a los 600 s quedaron `cargo` del propio worktree vivos y el siguiente run se
   negó a arrancar. El mensaje es correcto; falta matar el grupo de procesos
   del run anterior.
5. **Squash + snapshots**. Un snapshot que declara el tip de una rama deja de
   ser ancestro tras el squash-merge; el ratchet M2 lo tolera solo dentro de
   5 commits. Los snapshots se refrescan contra el HEAD de `main`.
6. **`fmt` rojo en `main`**. PR #371 (CU-2.4) entró con
   `cu2_w4_live_consumer.rs` sin formatear; el gate de esta release lo detectó
   en el `fmt` del árbol de main. Se corrigió en el PR de docs.

## Lecciones de operación con actores concurrentes

- El checkout compartido cambia de rama bajo los pies: dos gates fallaron
  (`fmt`, `contracts`) por el árbol de otro actor, no por el de la rama. La
  única forma de que el veredicto sea atribuible es correr el gate desde un
  checkout propio y con `CARGO_TARGET_DIR` propio; `pipelinek` usa el `cwd`
  (medido con sonda), así que un worktree sirve, pero el target dir global y
  `/tmp/cognicode-logs` siguen siendo compartidos.
- Los appends al JOURNAL y los snapshots de CURRENT.md chocan en cada rebase
  con los PRs de docs de otros agentes. Un fichero de veredicto por release
  (este) no choca nunca.
