3. Decisiones Escaladas

E1: ¿Estrategia de escritura — inherent methods vs. trait?

Pregunta: ¿Agregar save_call_graph(&CallGraph) y load_call_graph() como métodos inherentes en PostgresRepository, o crear un nuevo trait async (GraphPersistence)?

OpciónOSRatingClasificación
A: Métodos inherentes en PostgresRepository — save_call_graph(&CallGraph) y load_call_graph() como pub async fn. Sin trait nuevo. Sin cambios en la API pública excepto los métodos. 0.832 🟢 EXCELENTE 🔧 Técnico
B: Nuevo trait async GraphPersistence — Trait con #[async_trait], 2-3 métodos. PostgresRepository lo implementa. Futuros backends pueden implementarlo. 0.798 🟢 EXCELENTE 🔧 Técnico
C: Extender Repository trait — Agregar save_graph/load_graph al trait existente. Mezcla responsabilidades de lectura y escritura. 0.535 🟡 BUENO 🔧 Técnico

Recomendación del agente: Opción A — Métodos inherentes. El patrón es consistente con el approach existente: insert_edge() ya es pub(crate) inherente, no en trait. Un trait async añade superficie de API innecesaria para un solo implementador. Si en el futuro un segundo backend necesita el mismo contrato, extraer el trait es barato (refactoring mecánico). La simplicidad del approach inherente permite que este slice sea estrecho (~300 líneas), revisable, y libere el desbloqueo estratégico rápidamente.

E2: ¿Almacenar el blob bincode en PostgreSQL o solo tablas normalizadas?

Pregunta: SQLite almacena CallGraph como blob bincode (tabla call_graphs) Y pobla tablas symbols/call_edges. ¿Debe PostgreSQL hacer lo mismo (dual storage) o solo tablas normalizadas?

OpciónOSRatingClasificación
A: Solo tablas normalizadas — save_call_graph escribe a symbols + call_edges. load_call_graph reconstruye desde las tablas. Sin blob. Sin tabla call_graphs en PG. 0.820 🟢 EXCELENTE 🔧 Técnico
B: Dual storage (blob + tablas) — Agregar tabla call_graphs en PG, almacenar bincode, y también poblar symbols/call_edges. Consistente con SQLite. 0.650 🟡 BUENO 🔧 Técnico

Recomendación del agente: Opción A — Solo tablas normalizadas. PostgreSQL es la tienda canónica de query, no de blob. El roadmap explícitamente dice: "JSON graph snapshots are export and import only; the canonical state of truth is in PostgreSQL." El blob bincode es un artefacto de serialización que pertenece al path SQLite (donde no hay tipos nativos para queries complejas). En PostgreSQL, las tablas normalizadas SON la verdad canónica. load_call_graph se implementa como SELECT * FROM symbols + SELECT * FROM call_edges → reconstrucción en memoria. Esto es más lento que cargar un blob, pero aceptable para el MVP (sub-10k símbolos) y se optimiza después si es necesario.
