# Product manifest

`product-manifest.json` is the canonical product-level projection for the first public surface. It is generated, not hand-edited.

## Generate

```bash
python3 scripts/product/generate_product_manifest.py \
  --source-commit "$(git rev-parse HEAD)"
```

The committed artifact records the exact source commit used as generation input. A release or site sync may pass an explicit source SHA so the provenance remains honest when the generated bytes are committed in a later Git commit.

## Validate a committed artifact

```bash
python3 scripts/product/generate_product_manifest.py \
  --source-commit "$(python3 -c 'import json; print(json.load(open("product/product-manifest.json"))["source_commit"])')" \
  --check
python3 -m json.tool product/product-manifest.json >/dev/null
```

The JSON Schema is `product/schemas/product-manifest.v1.schema.json`.

## Ownership boundaries

- `public_surface.mcp.tool_catalog` points to the generated `crates/cognicode-core/product/tools.json`. Tool definitions remain authoritative in the runtime MCP registry. A-004 publishes a normalized projection from a real `tools/list` capture and never duplicates the registry.
- `product/tool-catalog-runtime.json` is the captured `tools/list` input used to generate the committed catalog. It is provenance input, not a second tool registry.
- `crates/cognicode-core/product/tools.json` preserves runtime metadata, sorts by tool name, and represents undeclared output/cache/network fields as `null` with `requirements_status: "not_declared"`. Null is not a negative capability claim.
- `public_profiles` is **derived** from `product/profiles.json`. The product manifest no longer hard-codes a profile list. See "Public profiles and stability" below.
- Language entries currently prove parser presence only and are conservatively marked `experimental`. A-005 owns the evidence-backed support matrix.
- Platforms are limited to Linux GNU release lanes that already have release evidence. macOS and Windows are intentionally absent.
- Bundle and plugin manifests are separate installation contracts and are not replaced by this file.

## Language and platform matrices

`languages.json` and `platforms.json` are generated projections for public
claims. They do not replace the runtime parser registry or release workflows.

Generate and validate both matrices with the source SHA used for the product
snapshot:

```bash
python3 scripts/product/generate_support_matrix.py \
  --source-commit "$(git rev-parse HEAD)"
python3 scripts/product/test_product_support_matrix.py
```

The language matrix distinguishes parser presence from focused acceptance
coverage. A parser without focused acceptance evidence remains `experimental`.
The platform matrix marks only the two published Linux GNU lanes as
`certified`; the Linux musl CI lane is `experimental`, and deferred macOS and
Windows public targets are `unsupported` for the current release contract.

Schemas:

- `product/schemas/languages.v1.schema.json`
- `product/schemas/platforms.v1.schema.json`

## Public profiles and stability

`product/profiles.json` is the canonical product-level projection of install and declared profiles, and the only source the product-manifest reads for `public_surface.profiles`. It is generated, schema-validated and committed.

The contract surface (`cognicode.profiles/v1`) carries four profiles. Each carries a `stability`, an `install` boolean, a `mutating` boolean, the set of `components` and `skill_bundles` it ships, and one line of evidence:

| id           | stability    | install | mutating | components                                   | skill_bundles                |
|--------------|--------------|---------|----------|----------------------------------------------|------------------------------|
| `core`       | `stable`     | true    | false    | `cogh`, `cognicode`                          | `cognicode`                  |
| `reviewer`   | `stable`     | true    | false    | `cogh`, `cognicode`, `cognicode-mcp`          | `cognicode`, `cognicode-mcp` |
| `developer`  | `experimental` | false | true     | declared; not an install path                | `cognicode-developer`        |
| `experimental` | `experimental` | false | false | declared; stability bracket, no install path | none                         |

Honest contracts only:

- The release contract in `crates/cognicode-cli/src/cmd/release_contract.rs` is the single behavioural source for binary ids, profile lists per component, and `SkillBundleSpec.published` flags. The generator parses that file and projects it into the schema.
- `--profile core` and `--profile reviewer` resolve through `cogh`. The installer does NOT accept `--profile developer` or `--profile experimental` today; the contract states that explicitly via `install: false` so the public surface stays aligned with the runtime.
- The `mutating` field on `developer` reflects the existing `feature_flags.mutations = "developer-explicit"` posture and is not an enabling claim.

Generate and validate:

```bash
python3 scripts/product/generate_profiles.py \
  --source-commit "$(git rev-parse HEAD)"
python3 scripts/product/generate_profiles.py \
  --source-commit "$(git rev-parse HEAD)" --check
python3 -m pytest -q scripts/product/test_profiles.py
```

Schema: `product/schemas/profiles.v1.schema.json`.

## Tool catalog

`crates/cognicode-core/product/tools.json` is the **master catalog**: every tool the product
publishes, including the ones a default build does not expose. The runtime
list is the **active subset**. They are not the same set, and capturing the
wrong one is silent — it produces a smaller catalog that still validates.

Five of the tools that a default build hides are gated by three features:
`program-analysis-server` (`interproc_summary`), `evidence-cli-ladybug`
(`list_evidence` and `search_evidence`) and `contract-store`
(`generate_contract` and `validate_contract`). Build with all three, or the
capture comes up short and the catalog stops describing the surface the
runtime publishes. Measured 2026-11-06: a default build reports 74 tools,
and a build with the three features reports the 88 the catalog publishes.

## The surfaces (`--profile`)

The MCP server publishes **one surface**, and the surface says what is
announced in `tools/list`. TASK-84 added three:

| profile   | what it announces                                                        |
|-----------|--------------------------------------------------------------------------|
| `default` | the five goals that answer before the analysis (`status`, `context`, `find`, `inspect`, `trace`) — measured 4.350 bytes for the list over the wire |
| `full`    | every goal and every tool: the 88 entries the master publishes           |
| `legacy`  | the 78 tools, each with the notice that names the goal that replaces it  |

`--profile` is **not** the install profile (`core`, `reviewer`, `developer`,
`experimental`): the install profile decides what the server may *do*, and
this one decides what it *announces*. The server's default is `default`: an
agent that connects gets the small list, and a client that still needs the
tools asks for `--profile legacy` (the tools, with the deprecation notice) or
`--profile full` (both).

The profile decides what is **announced**, not what is refused: a tool that
is not announced can still be called, and the read-only posture is what
refuses a writer.

Capture what the runtime really publishes — in the `full` surface, because it
is the only one that publishes every entry of the master:

```bash
cargo build -p cognicode-mcp \
  --features cognicode-core/program-analysis-server,cognicode-core/evidence-cli-ladybug,cognicode-core/contract-store
/var/home/rubentxu/cargo-targets/debug/mcp-client \
  --workspace "$PWD" \
  --method tools/list \
  --server-binary /var/home/rubentxu/cargo-targets/debug/cognicode-mcp \
  --server-profile full \
  > product/tool-catalog-runtime.json
```

The capture is the runtime's own answer, so it carries what the runtime
publishes: the input schema, the derived output contract and the behaviour
hints (`readOnlyHint`, `destructiveHint`, `idempotentHint` and
`openWorldHint`). The hints are not in the master on purpose — the runtime
derives them from the `authority` the master declares, and a second copy
would be a second source of truth.

The input schema is derived too: the runtime derives it from the struct that
reads the tool's arguments, so the shape a client builds a call from is the
shape the server honours.

**`crates/cognicode-core/product/tools.json` is hand-authored. Do not write the generator's output
over it.** The generator does not own nine of the fields (listed below), so
running it over the master drops all nine. Use it to see what the runtime
would publish, and compare that against the committed document:

```bash
python3 scripts/product/generate_tool_catalog.py \
  --input product/tool-catalog-runtime.json \
  --output /tmp/tools.generated.json \
  --source-commit "$(git rev-parse HEAD)"
```

The committed master and the capture are compared by
`scripts/ci/test_conditional_write_contracts.py`. It fails when they
disagree about a tool's input schema — the tool names can agree while the
shape the consumer passes has drifted — and also when they disagree about the
`runtime_metadata`: the master's mirror of what the runtime publishes has to
say the runtime's own version, not the version of the day the entry was
authored.

Validate the committed projection with:

```bash
python3 scripts/product/test_product_tool_catalog.py
```

The catalog schema is `product/schemas/tools.v1.schema.json`. An output
schema is `null` for the tools that publish no contract, and it is the
**derived** contract for the tools that do: the runtime derives it from the
type that serialises the answer, and the catalogue publishes that same
contract rather than a hand-written copy of it. A copy is a second
description of a shape, and the copy is the one that rots —
`crates/cognicode-core/tests/it/b2_w3_output_schema_contract.rs` compares
the two byte for byte so they cannot drift apart unnoticed.

### Fields the generator does not own

`limitations`, `required_args`, `prerequisites`, `follow_ups`, `intent_tags`,
`language_scope`, `feature`, `impact_direction_floor` and `precision_floor`
are present in the published catalog and are **not** produced by
`generate_tool_catalog.py`: the runtime's `_meta.cognicode` carries no source
for them. Running the generator over the master therefore drops all nine.
They are curated by hand and stay hand-authored: the decision that the master
is never regenerated is recorded in `docs/roadmap/JOURNAL.md`.

### Keeping the master's mirror of the runtime honest

Two fields of the master are mirrors of what the runtime publishes, and both
are synchronized, never regenerated.

`runtime_metadata` is the mirror of what the runtime publishes in
`_meta.cognicode`, `tool_version` included, and the runtime injects that
version from `CARGO_PKG_VERSION` on every response. A mirror that is written
once and never revisited therefore drifts every time the runtime moves.

`input_schema` is the mirror of the `inputSchema` the runtime advertises,
and the runtime derives it from the struct that reads the arguments
(`crates/cognicode-core/src/interface/mcp/input_contracts.rs`). The same
argument applies: a hand-written copy of a shape is a second description of
it, and the copy is the one that rots. Four tools accepted an argument the
published schema never named, so a client that built its call from the
schema could not pass them.

The vocabulary of an argument is derived with it. Where the argument is an
enumeration — the mode `read_file` reads, the shape `codebase_map`
publishes — the published shape names the values the server accepts,
because the type that names them is the type the server reads. A value
outside that list is a rejection; the server used to accept some of them in
silence, and a `read_file` whose mode does not exist came back with the
whole file.

```bash
python3 scripts/product/sync_tool_catalog_with_the_capture.py
python3 scripts/product/sync_tool_catalog_with_the_capture.py --check
```

The synchronization is a merge. It takes from the runtime the keys the runtime
publishes and leaves everything else alone: the nine fields above, the tool
set, and the curated keys the runtime does not publish — `check_architecture`
carries `gate_authority` and `produces_observations_only`, which no
`tools/list` will ever return, and a copy would take them away. `--check`
proves the committed master is a fixed point of that merge, and
`scripts/ci/test_conditional_write_contracts.py` fails when the
committed master stops being one.

The capture is the reference, and it is provenance: it is a real `tools/list`,
so it has to be refreshed when the runtime moves. A capture that has gone
stale proves nothing.
